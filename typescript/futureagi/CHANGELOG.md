## 0.3.1

### Changed

* A request that carries a key to a plain-http host that is not loopback is refused before any connection is made, with an `Error` whose `code` is `insecure_http_origin`. A request carries a key when it has an `X-Api-Key`, `X-Secret-Key` or `Authorization` header (any scheme), a `Proxy-Authorization` header that you set or a `Cookie` header, any other header whose name holds `api-key` (or `api_key`, `apikey`), `secret`, `token`, `passw`, `credential`, `auth`, `session` or `cookie` in any letter case, axios `auth` credentials, or a user name or password in the base URL or the request URL. For `HttpClient` and `APIKeyAuth` these headers are read from every source at the same point: the request headers, the client defaults, headers an interceptor adds, and `fetchOptions.headers`, which the client reads as request headers (a name in both takes the `fetchOptions.headers` value) and removes from `fetchOptions`. For `HttpClient` and `APIKeyAuth` the request is read as it is sent: after interceptors and `transformRequest`, and, for an adapter wrapper that hands the request to the client's adapter or to the axios http adapter, after that wrapper. This covers `HttpClient`, `APIKeyAuth` and the platform `Client`.
* On the SDK's own transport, the SDK drops your key on a redirect to any address other than the one you configured, within the limits for an adapter function of your own given below.
* A request sent through your own axios transport or adapter, for example one that follows redirects itself, is not re-checked when it is redirected, so the redirect can carry your API key to another host, including one over plain HTTP. Use the SDK's default transport, or turn redirects off in your own.
* For `HttpClient` and `APIKeyAuth`, the client follows a redirect itself, one hop at a time, with the axios http adapter, the axios `fetch` adapter, or an adapter function of your own that hands the request to one of them, and judges each hop. A hop to the origin of the first request keeps its headers and is judged by the same rule as the first request. A hop to any other origin (another host or port, or https to http) is sent without any of the headers named above that carry a key (`X-Api-Key`, `X-Secret-Key`, `Authorization`, `Proxy-Authorization`, `Cookie` and the other credential names) and without axios `auth`. When the first request carried a key, every later hop that leaves its origin for plain http is refused with that `Error` (code `insecure_http_origin`), and not retried, unless the host of the hop is loopback and the opt-in is set. When redirects are followed (`maxRedirects` is not 0 and `fetchOptions.redirect` is not `manual` or `error`) and the method is not GET or HEAD, a streamed request body (such as a `form-data` upload) is read into memory before the first request, so that a 307 or 308 hop can send it again. The copy holds at most `maxBodyLength` bytes, or 10 MB when `maxBodyLength` is not set: a body over a given `maxBodyLength` is refused with code `ERR_FR_MAX_BODY_LENGTH_EXCEEDED`, and a longer body without one is sent as a stream with no copy, so a hop within the origin that sends the body again (a 307 or 308, a 300, or a 301 or 302 when the method is not POST) fails with that code. A source that closes before its end while it is read into memory fails the request with code `ERR_BAD_REQUEST`. When the source of a stream sent with no copy closes or fails before its end, the request fails with the error of the stream (code `ERR_STREAM_PREMATURE_CLOSE` for a stream that closes without one) and does not wait for its `timeout`. Reading the body is bounded by the request `timeout` (code `ECONNABORTED`, or `ETIMEDOUT` with `transitional.clarifyTimeoutError`), its `signal` and its `cancelToken` (a `CanceledError`); when one of them ends it, the source stream is destroyed. When redirects are followed, a streamed body that was already read, ended, destroyed or failed is refused at once (code `ERR_BAD_REQUEST`), and `HttpClient` does not retry a request whose streamed body was read. `maxRedirects` and a `fetchOptions.redirect` of `manual` or `error` are respected. The platform `Client` follows a redirect only within the origin of its base URL; a redirect to another origin rejects with an `APIConnectionError`.
* An adapter function of your own is covered as far as it hands the request to the client's adapter, the axios http adapter or the axios `fetch` adapter. A key that it adds and sends through the axios `fetch` adapter or `fetch` itself is not read for the plain-http rule (a redirect of that request is judged from the headers it carried). It is called again for each redirect hop, and a key it adds on a hop to another origin is sent. It is not called for a keyed plain-http request, or hop, that the client sends directly to its host: the client sends that one with the axios http adapter itself. A redirect that it follows itself, not reading `maxRedirects` or `fetchOptions.redirect`, is not judged. A key that it adds before the axios http adapter is read by an agent that a process-wide wrapper of `http.request` can replace. A proxy that it sets (the axios `proxy` option, in the config it is given or in a copy of it) is read when the request is created: a keyed https request, or an https hop of one, that would reach that proxy outside a tunnel is refused, as described below, also when the client had chosen a tunnel for it. A `Proxy-Authorization` that the adapter function adds to a request addressed to that proxy goes to that proxy and is not read as a key; a `Proxy-Authorization` that you set makes the request keyed, so it is refused when the adapter function sends it to a proxy that it sets. A request that goes through a proxy it sets with a user name and password of its own counts as carrying a key on a hop to another origin (the client reads the proxy's own `Proxy-Authorization` only for the proxy it chose before the adapter function ran): such a hop to plain http, or one that would send the body again, is refused. In the config that an adapter function receives outside a tunnel, `httpAgent` and `httpsAgent` are as you set them (unset when you set none): an adapter function that fills in an agent you left unset sends the request with that agent, and the proxy is judged on the agent the request uses. An adapter function that replaces the `transport` the client set sends the request with what it sets. Through a proxy, the SDK uses the agent you pass when the client is created; an httpsAgent set later in an adapter or interceptor is not used, so certificate pinning must be set on the client's agent.
* `allowInsecureHttp: true` in the client options allows such a request; when the option is not given, `FI_ALLOW_INSECURE_HTTP=1` does. Only `true` or the exact string `"1"` enables it, and a given option is used in place of the environment variable, so an explicit `allowInsecureHttp: false` wins over `FI_ALLOW_INSECURE_HTTP=1`. `KnowledgeBase` and `Annotation` (in their options), `ProviderAPIKeyClient` (an options argument after `fiBaseUrl`, and the options of its static methods) and `APIKeyManager.getInstance` and `getAPIKeyManager` (for the call that creates the instance) take the option as well. `Annotation` passes the refusal on with its `code`. `Prompt.open()` sends its template lookups with the options of the instance (`allowInsecureHttp`, `timeout` and the others), and passes a refusal of a lookup on with its `code` in place of reading it as a missing template. `KnowledgeBase` (`listKbs`, `createKb`, `updateKb`, `deleteFilesFromKb` and `deleteKb`, also with `kbNames`) and `APIKeyManager.validateRequiredProviders` reject with the refusal itself, so its `code` is on the error you receive; `deleteKb` does not read a refused name lookup as a name that was not found, and `validateRequiredProviders` does not read it as a missing provider key. When the name lookup that the `KnowledgeBase` constructor starts is refused, it settles without an unhandled rejection, and the next call on that client meets the same refusal. `createKb` with a name and no files (or an empty list) sends the create request in place of failing with `The provided list of file paths is empty.`
* A keyed plain-http request that is sent (to a loopback host, or with the opt-in) goes directly to its host through an `http.Agent` of the SDK: it does not use a proxy setting, the global `http.Agent`, the global dispatcher, a replaced global `fetch` or the runtime's environment proxy. `HttpClient` sends it with the axios http adapter, whatever adapter is configured. Both `HttpClient` and the platform `Client` create the request with `http.ClientRequest` and the SDK agent, so a process-wide wrapper of `http.request` (for example `global-agent` with `forceGlobalAgent`) does not choose its agent, and refuse it when that agent was replaced. A `Proxy-Authorization` header that you set is not sent on this route, as no proxy is on it (through a proxy it goes only on the `CONNECT`, as described below): the SDK drops it from a keyed plain-http request that it sends directly to its host, and from the keyed loopback request that the platform `Client` passes to the runtime's `fetch` in a runtime without Node's `http` module.
* With a `fetch` given in the platform `Client` options, a keyed request to a loopback host is passed to that `fetch`, and a keyed request to any other plain-http host is refused, with or without the opt-in.
* Requests that carry your key go through a proxy only inside an encrypted tunnel. When a proxy applies to a keyed request to an https address, the SDK opens a `CONNECT` tunnel through that proxy and runs TLS to the host inside it. For `HttpClient` and `APIKeyAuth` the proxy is chosen as the axios http adapter chooses it: the axios `proxy` option when it is given (`proxy: false` means no proxy), else `HTTPS_PROXY`, `https_proxy`, `ALL_PROXY`, `all_proxy` or the `npm_config_https_proxy` and `npm_config_proxy` variables, unless `NO_PROXY`, `no_proxy` or `npm_config_no_proxy` names the host (a host, a domain with a leading `.` or `*`, an optional `:port`, or `*`). A request with the axios `socketPath` option uses no proxy, as in axios. For the platform `Client` that uses the runtime's `fetch`, the same environment variables are read, whether or not the runtime's `fetch` reads them. The proxy receives `CONNECT host:port`, a `Host` header and, when the proxy address holds a user name or the `proxy` option holds a user name or password, a `Proxy-Authorization: Basic` header made from them; the request itself, with every header that carries a key, goes inside the tunnel, and the proxy user name and password do not go to the host. TLS inside the tunnel checks the certificate against the host's name or IP address, with Node's default CAs, or with the TLS settings (such as `ca` and `rejectUnauthorized`) of an `https.Agent` given as the axios `httpsAgent`. When the proxy answers the `CONNECT` with a status other than 200, the request fails and is not sent another way. The request `timeout` (the `timeout` of the platform `Client`) also bounds the wait for the tunnel, and a request that is canceled or aborted while its tunnel is being opened closes its connection to the proxy. A `Proxy-Authorization` header that you set on a keyed request is sent on the `CONNECT` when the proxy address and the `proxy` option hold no user name or password (else the header made from them is sent), also on the `CONNECT` of a redirect hop within the origin, and it does not go inside the tunnel to the host. When a request carried a key, every later hop of it to an https address goes through the tunnel as well, also when its key headers were dropped.
* This covers the axios http adapter, the axios `fetch` adapter (a keyed request for which a proxy applies is sent with the axios http adapter instead), an adapter function of your own that hands the request to the axios http adapter, every redirect hop, and the platform `Client` with the runtime's `fetch`. With a `fetch` given in the platform `Client` options, https requests are passed to that `fetch`.
* A keyed request for which a proxy applies is refused with the `Error` whose `code` is `insecure_http_origin`, before any connection is made, when the proxy is not an http or https proxy (for example `socks5://`) or the proxy address in the environment cannot be read. A keyed https request that would reach a proxy outside a tunnel (a key that an adapter function of your own adds after the client read the request, or a proxy that it sets on a keyed request) is refused with the same code when the request is created. The opt-in (`allowInsecureHttp` or `FI_ALLOW_INSECURE_HTTP=1`) does not change these refusals, and it does not send a keyed request to a proxy: a keyed plain-http request that is sent goes directly to its host, as described above.
* For `HttpClient` and `APIKeyAuth`, a redirect to another origin that would send the body again (a 307 or 308, a 300, or a 301 or 302 when the method is not POST) is not followed when the request carried a key and has a body: that body can hold a key as well (the provider key that `ProviderAPIKeyClient.set` sends, for example). The call rejects with the `Error` whose `code` is `insecure_http_origin`, also for a streamed body over the copy, and nothing is sent to the other origin or to a proxy for it. A redirect within the origin sends the body again; a 301 or 302 of a POST and a 303 go on as a GET without the body.
* A `Proxy-Authorization` header that axios makes from the proxy's own user name and password (in the proxy address of the environment or in the `proxy` option) is addressed to the proxy and does not make a request keyed: a request without a key goes through such a proxy as axios sends it, and a hop to another origin whose key headers were dropped is not refused for it.
* Loopback hosts are `localhost`, `127.0.0.0/8` and `::1`. The plain-http refusal and the direct route do not apply to requests to https addresses. Requests without a key go through a proxy as axios chooses it: the axios `proxy` option, or for an https address `npm_config_https_proxy`, `HTTPS_PROXY` or `https_proxy`, and for a plain-http address `npm_config_http_proxy`, `HTTP_PROXY` or `http_proxy`, then `npm_config_proxy`, `ALL_PROXY` or `all_proxy`, unless `NO_PROXY`, `no_proxy` or `npm_config_no_proxy` names the host.
* `HttpClient.request` passes on an error that came with no HTTP response (a refused or unreadable body, a timeout, a TLS or proxy failure; the wait for a proxy tunnel that runs past the request `timeout` has code `ETIMEDOUT`) as the axios error with its `code`, in place of a `ServerError` with the message `HTTP 500`. It does not send again a request that was refused: codes `ERR_BAD_REQUEST`, `ERR_CANCELED` and `ERR_FR_MAX_BODY_LENGTH_EXCEEDED`, a TLS certificate error, or a proxy that answered the `CONNECT` with a status other than 200; a request that exceeds `maxRedirects` rejects at once with code `ERR_FR_TOO_MANY_REDIRECTS`. A streamed body whose reading has started is not sent again by a retry.
* `APIKeyAuth` uses an `fiApiKey` or `fiSecretKey` given in its options as given, also when it is empty (it then reports the key as missing), and reads `FI_API_KEY` and `FI_SECRET_KEY` only for an option that is not given.
* In the platform `Client`, headers given as a `Headers`, a `Map` or a list of `[name, value]` pairs, per call or in `defaultHeaders`, are read as headers.
* The SDK checks where a request goes before your own adapter or transport runs. If that code changes the request afterwards, for example by handing it to another axios adapter, adding a proxy, or changing its URL, agent or DNS lookup, the change is not re-checked, and your API key can reach the new destination, through a proxy in plain text.
* Sending a request through the client's own axios instance yourself, for example resending the config from an error or response after a cross-origin redirect, adds the client's key headers to wherever that request goes.
* Keyed requests through a proxy need axios 1.7 or later; with axios 1.6 they fail with an error.
